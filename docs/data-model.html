    Interactive reference generated from docs/DATA-MODEL.md. Extracted directly from the prototype's TypeScript source (src/lib/cabinet/*) plus every route/component that reads or writes each field — the authoritative field-by-field, table-by-table inventory to carry into the real app.

    ⚠️ Scope note: vaccinations, documents, payments and analyses are intentionally excluded (out of scope for now), even though the CabinetData type still declares those four collections (Vaccination, CabinetDocument, Payment, Analysis / AnalysisValue). If they come back in scope later, re-derive their sections from src/lib/cabinet/types.ts and tracking.ts.

    1. High-level shape

    CabinetData (types.ts:339) is the root object — the "database". Of its 17 arrays + 1 embedded config object, the 13 in-scope collections documented here are listed below. There is no cabinet_id / tenant column anywhere — the prototype is single-practice by construction.

    2. Entity-relationship diagram

    Every "FK" below is a plain string equality match, resolved client-side (Array.find(x => x.patientId === id)). Nothing prevents an orphan patientId today; a real schema must add real foreign keys + cascade rules (§8).

    3. Tables in full detail

    Every field, its TypeScript type, optionality, meaning, and where it's read/written in the UI. Click a row to expand. Table = top-level CabinetData array · Embedded = nested inside another row/object · Singleton = one instance, no array · Unused = typed & seeded but not wired to any screen yet.

    4. Session / runtime state (not persisted)

    Held in React state inside CabinetProvider (store.tsx), exposed via useCabinet() (context.ts). Not part of CabinetData and vanishes on reload.

    Real app equivalents: offline/pending/syncing map to a real offline-sync/PWA design (HOPE-V2-08, explicitly out of v1 scope); locked/lockDelay map to HOPE-AUTH-04; currentUser/role/isAdmin map to a real JWT session (HOPE-AUTH-01, HOPE-AUTH-06).

    5. Static reference data (shipped as constants)

    Not stored per row — reference content served the same way to every tenant.

    6. Cross-cutting derived / computed logic

    Pure functions over the tables above — important to reproduce server-side (or in shared logic) so the real app's numbers match.

    tracking.ts's marker/trend/score helpers (markerSeries, inRange, analysisScore, markerTrend, globalTrend) operate on Analysis[] data and are out of scope per the exclusion above.

    7. Security / data-hygiene issues

    Visible directly in this schema — carried over into the real app's design (matches the HOPE-AUTH-* tickets).

      A straightforward mapping of §3 into SQL tables, adding what's missing (tenant key, timestamps, versioning) without changing the product's actual data shape. Postgres-flavored; adapt for SQLite if building a local .exe with an embedded DB.
